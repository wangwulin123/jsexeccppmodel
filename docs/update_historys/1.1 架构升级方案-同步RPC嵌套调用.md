## 一、背景与问题

### 1.1 目标场景

前端通过 JSAPI 同步 RPC 调用 C++ 函数，C++ 函数内部**同步**事件通知前端，前端在事件回调里再**嵌套**发起同步 RPC：

```
JS: Extention.node.funcxxx()                        ── 同步 RPC
  └─ C++ funcxxx 内 DispatchEventSync("ev", args)   ── 同步事件，等回调返回值
       └─ 前端回调 listener("ev", args) { ... }
            └─ return Extention.node.funcxxx2(x)    ── 嵌套同步 RPC
       ◀─ 回调返回值送回 C++
  ◀─ funcxxx 拿到返回值，继续执行并返回
```

### 1.2 结论

当前架构**不支持**该场景：三个线程层面死锁 + 一处协议缺失 + 一处多页面竞态（详见第二章）。

当前唯一能工作的退化形态：funcxxx 内 `BroadcastEvent` 不等待 → 外层调用先返回 → 事件后派发 → 回调里调 `funcxxx2` 作为**顶层调用**正常执行。即"伪嵌套"可用，真嵌套不可用。

## 二、现状调用链与死锁分析

### 2.1 现状调用链（含线程归属）

```
[Renderer 主线程]  funcxxx() → SyncChannel::Send
                    写请求共享内存 → SetEvent → 阻塞 WaitForSingleObject(reply_event, 10s)   ← 阻塞点①
[Browser SyncLoop 线程]  读请求 → HandleSyncPayload → RunOnMainThread (BlockingQueuedConnection)
[Qt GUI 线程]      rpc_.Process → funcxxx C++ 代码执行
                    BroadcastEvent → OnEvent → CefPostTask(TID_UI)   ← 异步投递，不等结果
[CEF UI 线程]      EventDispatchTask → SendProcessMessage(PID_RENDERER, jsapi.event)
[Renderer 主线程]  （仍阻塞在①）…… OnProcessMessageReceived 无法执行
```

### 2.2 死锁链路分析

**阻塞点① — 渲染进程阻塞等待期间无法接收事件**

`SyncChannel::Send`（`src/bridge/jsapi_render_handler.cpp:263`）中 `WaitForSingleObject(event_, 10000)` 纯阻塞，不泵消息。`jsapi.event` 进程消息要等渲染主线程回到 CEF 消息循环才能投递——即**事件只会在外层同步调用返回之后才派发**，顺序倒挂。即使 funcxxx 只是 fire-and-forget 地发事件，"同步通知"也不成立。

**阻塞点② — Browser 侧 SyncLoop 单线程被占用**

`SyncLoop`（`src/bridge/jsapi_browser_bridge.cpp:204-219`）是唯一的工作线程，处理请求期间阻塞在 `RunOnMainThread` 等 Qt GUI 线程返回。即使①解决（渲染进程能在等待期间重入执行回调），回调里的 `funcxxx2()` 写请求共享内存并 SetEvent 后——嵌套请求**无人读取**。

**阻塞点③ — Qt GUI 线程被外层执行占据**

`SetMainThreadDispatcher`（`apps/qt_host/main.cpp:69-76`）将插件函数执行投递到 Qt GUI 线程（BlockingQueuedConnection）。即使②解决（读/执行分离），`funcxxx2` 的执行任务排到 Qt GUI 线程队尾——而 Qt GUI 线程正在 funcxxx 里等待事件回执。funcxxx 不泵消息，队列不前进，**经典重入死锁**。

**协议缺失 — 事件没有回执通道**

事件消息不带关联 ID，`HandleEvent`（`src/bridge/jsapi_render_handler.cpp:761`）里 `ExecuteFunction` 的返回值直接丢弃。C++ 侧"同步等前端回调返回值"在协议层就不可表达——这是比死锁更根本的问题。

**隐藏雷点 — process_mutex_ 非递归锁**

`HandleSyncPayload`（`src/bridge/jsapi_browser_bridge.cpp:271-274`）的 `process_mutex_` 在 `rpc_.Process` 期间持有。嵌套调用最终在同一 Qt GUI 线程重入执行时，嵌套的 `Process` 会再次锁这个非递归 mutex——死锁。升级时必须一并处理。

**多页面竞态 — 请求通道全局单槽（v1.1 新识别）**

请求通道 `Local\jsapi_req` 无 PID 隔离（`include/jsapi_bridge/jsapi_protocol.h:30-43`），回包通道却按 PID 隔离。多个渲染进程（多 web 页）并发同步调用时：互斥量只保护写与写、不保护写与读——渲染进程 A 写完释放互斥量后、SyncLoop 读取前，渲染进程 B 可覆盖同一槽，**A 的请求静默丢失**，等 10s 超时；auto-reset event 还会把两次 SetEvent 合并成一次唤醒。即使不丢，也是单槽 + 单 SyncLoop + 单 Qt GUI 线程 + process_mutex_ 四点叠加的全局严格串行。

## 三、设计目标

1. 支持完整的同步 RPC 嵌套调用：C++ 同步事件能拿到前端回调返回值，回调内可再发嵌套同步 RPC；
2. 全链路无循环等待，JS 单线程语义不破坏（回调与嵌套调用都在同一 V8 栈上重入执行）；
3. 多页面（多渲染进程）并发同步调用安全：无丢请求竞态，无因竞态导致的超时；
4. 存量插件、存量前端页面零改动；
5. 有明确的嵌套深度、对齐校验与超时保护边界，行为可预期。

## 四、已确认的设计决策

| # | 决策点 | 选型 | 说明 |
|---|--------|------|------|
| 1 | 目标语义 | **完全同步事件** | C++ 能拿到前端回调的返回值并据此决定后续行为（类似 WPS OnBeforeSave 可取消）。需要 event_result 回执通道 + 双端泵消息，复杂度最高，但语义完整 |
| 2 | 插件执行线程模型 | **保持 Qt GUI 线程；等待策略为内联等待循环（v1.1 修订）** | 业务节点仍可直接操作 Qt 控件。funcxxx 等事件回执时进入专用等待循环：**就地内联执行**嵌套请求（复刻 WPS WaitLevelFinish 模式），只派发跨线程 sent 消息、**不泵 posted、不进 Qt 事件循环**——彻底规避 v1.0 QEventLoop 方案的 Qt 重入风险 |
| 3 | 兼容策略 | **统一事件通道改造** | 同步/异步事件走同一套共享内存通道，不再保留进程消息派发路径。事件派发摆脱 CEF UI 线程依赖 |
| 4 | 保护边界 | **深度限制 + 每层超时 + 栈对齐校验（v1.1 增强）** | 嵌套深度上限 8 层；每层超时默认 10s 可参数化；execute_level 与 nest_level 对齐校验作为栈不齐的防线 |
| 5 | 阻塞期间异步事件 | **暂存到外层返回后** | 同步等待期间到达的异步事件暂存 stash 队列，最外层调用返回后按序派发。语义保守，与现状时序基本一致 |
| 6 | DispatchEventSync 返回语义 | **三态可区分** | 沿用项目 error 出参风格，成功 / 无监听 / 超时 / 深度超限 / 通道溢出 / 栈不齐可区分 |
| 7 | 多页面并发（v1.1 新增） | **请求通道按 PID 隔离 + 引导握手 + 会话串行** | 消除单槽竞态；执行侧沿用 WPS 会话模型：Qt GUI 线程同一时刻只服务一个渲染进程的会话，页面间排队、各自不丢请求 |

## 五、总体架构

### 5.1 升级前后对比

```
【升级前】
Renderer 主线程 ──全局单槽请求shm──▶ SyncLoop 线程 ──BlockingQueued──▶ Qt GUI 线程
     ▲                            │                              │
     └──────回包shm◀──────────────┘                              │ CefPostTask(TID_UI)
Renderer 主线程 ◀────jsapi.event 进程消息──── CEF UI 线程 ◀─────────┘
  （阻塞期间收不到 → 事件顺序倒挂；嵌套请求无人读 → 死锁；多页面共写单槽 → 丢请求）

【升级后】
Renderer 主线程 ──per-pid请求shm──▶ 通道读取器（线程池，读/执行分离）
     ▲    ▲                          │ execute_level==0: 顶层请求
     │    │                          │   → QueuedConnection 投递 GUI 任务
     │    │                          │   { BeginLevel; Process; 写回包; EndLevel }
     │    │                          │ execute_level>0: 嵌套请求/event_result
     │    │                          │   → 嵌套队列 + SetEvent(nest_evt_<pid>)
     │    │                          └─ 回到等待（永远不因执行而停止等待）
     │    │
     │    └─handoff（同步事件，嵌套栈重入执行）◀── watcher 线程 ◀── evt 环形缓冲 ◀─┐
     └──────per-pid回包shm◀── GUI 任务内写回                                      │
                                                                                   │
Qt GUI 线程（会话中）: Process → funcxxx → DispatchEventSync ───────────────────────┘
                       → BeginLevel → 写 evt 通道 → 内联等待循环
                         MsgWait{nest_evt, abandon, QS_SENDMESSAGE}
                         醒于 nest_evt → pop 嵌套队列 → 就地内联 Process（嵌套请求）
                                          或 完成 invoke（event_result 到达）
```

### 5.2 核心机制一览

| 机制 | 解决的问题 | WPS 对应物 |
|------|-----------|-----------|
| 事件环形缓冲通道（按渲染进程 PID 隔离） | 统一事件派发路径，支持积压 | — |
| 渲染侧 watcher 线程 + handoff/stash 分流 | 阻塞点①：阻塞期间事件可注入 / 暂存 | — |
| 通道读取器读/执行分离 + 嵌套路由 | 阻塞点②：嵌套请求随时可读、可路由 | MainEvent 监听 |
| 内联等待循环（只派发 sent，不泵 posted） | 阻塞点③：嵌套请求就地执行，无 Qt 重入 | WaitLevelFinish + MsgWait(QS_SENDMESSAGE) |
| event_result 回执 + invoke 关联表 | 协议缺失：回调返回值送回 C++ | SetRpcReturn |
| execute_level / nest_level 双计数器 | 栈不齐防线；跨进程会话对号 | m_JsExecuteLevel / m_nNestLevel |
| 请求通道按 PID 隔离 + 引导握手 | 多页面单槽竞态；会话归属确定 | m_pJsApiIpcs 按 pid + CPM_SETBROWSERPROCESSID/NOTIFYEXEC 两段式 |
| process_mutex_ 条件退役（宿主设置 Poster 后移除；降级模式改 recursive 保留） | 隐藏雷点：同线程重入执行不死锁，且无 dispatcher 时不数据竞争 | — |

## 六、详细设计

### 6.1 通道与协议设计

#### 6.1.1 通道总览（v1.5：`<key>` = browser_id，两端各自 Ensure 对齐）

> v1.1 原设计按渲染进程 pid 隔离并配引导握手；v1.5 起 key 改为浏览器标识，命名格式不变（`<pid>` → `<key>`）。

```
请求通道（renderer → browser，单写者）：
  Local\jsapi_req_<key>          请求槽（1MB，含 pending 电平标志）
  Local\jsapi_req_evt_<key>      auto-reset 唤醒事件（加速器，非唯一依据）
  Local\jsapi_req_mutex_<key>    读/写互斥（防交错）

回包通道（browser → renderer，v1.3 电平化改造）：
  Local\jsapi_reply_<key> / Local\jsapi_reply_evt_<key>
  header 增加 reply_pending 电平标志（browser 写完置位、renderer 读完清除）
  ——与请求通道 pending 对称：auto-reset 信号只作加速唤醒，数据以标志 + seq 为准

事件通道（browser → renderer，统一同步/异步）：
  Local\jsapi_evt_<key>          事件环形缓冲（槽 1MB 与请求通道对齐，默认 4 槽；异步事件单条超限回退 kEventMessage 进程消息）
  Local\jsapi_evt_mutex_<key>    读写互斥
  Local\jsapi_evt_event_<key>    auto-reset 唤醒事件

嵌套通知（browser 进程内，读取器 → GUI 等待循环）：
  nest_evt_<key>                 进程内 auto-reset 事件 + 嵌套队列（进程内存，无需共享）

渲染进程退出通知（browser 进程内）：
  abandon_<key>                  进程内事件，OnRenderProcessTerminated 触发
```

**请求通道单写者自律**：渲染进程单线程写自己的通道，写后即阻塞等回包，天然串行——写-写无竞争；`pending` 电平标志（写方置位、读方清除，互斥量保护）取代纯信号驱动，**彻底消除读-写交错丢请求**：信号只是加速唤醒，数据以槽内标志为准，谁醒谁按会话状态分类，不会因信号被"错误一方"消费而丢数据。

#### 6.1.2 事件 payload 扩展

```json
{ "name": "...", "cb": 5, "args": [...], "invoke_id": 1, "frame": "..." }
```

`invoke_id > 0` 表示同步事件（需回执）；`= 0` 为异步事件（现状语义）。**渲染侧据此区分是否写回执、是否立即重入**。

#### 6.1.3 event_result 回执（复用请求通道）

回调执行完，返回值走该渲染进程的请求通道发回 browser，**不新建通道**：

```json
{ "op": "event_result", "invoke_id": 1, "value": {…} }
```

读取器对 `op == event_result` 的分类优先于会话状态判断（见 §6.3.1）。

### 6.2 渲染进程侧改造（`src/bridge/jsapi_render_handler.cpp`）

#### 6.2.1 新增事件 watcher 线程

统一通道下，渲染主线程非阻塞期间也需要有人盯事件通道（CEF 消息循环不可注入）。新增常驻 watcher 线程作为事件的**唯一接收者**：

```
watcher 线程：
  等 evt_event 唤醒 → mutex 内取槽读事件 →
    invoke_id > 0 且 sync_depth_ > 0  → handoff 队列 + SetEvent(handoff_event)  // 注入阻塞中的主线程
    invoke_id > 0 且 sync_depth_ == 0  → CefPostTask(TID_RENDERER, 派发)        // v1.3 第四路
    invoke_id == 0 且 sync_depth_ > 0  → stash 队列                             // 暂存，外层返回后派发
    invoke_id == 0 且 sync_depth_ == 0  → CefPostTask(TID_RENDERER, 派发)       // 走消息循环
```

**第四路说明（v1.3 补）**——`invoke_id > 0 且 sync_depth_ == 0`（异步 RPC 执行期间 C++ 发同步事件、前端主线程空闲）：若误走 handoff，无人在等 handoff_event → 回调滞留 → C++ 侧 10s 超时。正确行为：PostTask 到渲染主线程，回调在消息循环里执行，回执（event_result）照常经请求通道 → 读取器 → nest_evt 送达 GUI 等待循环（异步 RPC 的执行经阻塞 dispatcher 落在 GUI 线程，等待循环照常运转）；派发任务需携带 invoke_id 以写回执。回调只派发一次，无 at-least-once 迟到问题。

单一接收者设计**天然消除竞争**：不存在两方抢同一个 auto-reset event 的问题。

`sync_depth_` 为 atomic 深度计数：Send 进入等待前 +1（必须在写请求之前），退出等待后 -1；减到 0 时 drain 两个队列。

#### 6.2.2 SyncChannel::Send 改造

**v1.6 修正（性能）**：回包槽不再每次 `Reset`。`TryTake` 以 `reply_pending` 电平 + `seq` 双校验，
超时残留的旧回包因 seq 不匹配被丢弃，新回包 `Write` 时直接覆盖；省掉一次命名互斥量往返（约 5~10 µs/次）。
等待原语同时由 `MsgWaitForMultipleObjects(..., wake mask = 0)` 改为 `WaitForMultipleObjects`——
两者都不派发窗口消息，语义一致，但后者少一次消息队列检查。

**v1.3 修正（P0 级）— 锁作用域收窄**：现状 `Send` 顶部 `std::lock_guard<std::mutex> lock(mutex_)` 覆盖整个函数（含 10s 等待），嵌套重入 `Send` 在同一线程二次加锁 → **自死锁且无超时救济**。修正：锁只覆盖 `Ensure` + 回包槽重置 + 写请求，**等待期间不持锁**。嵌套 `Send` 重置回包槽是安全的——browser 侧 GUI 单线程会话串行，外层回包此时尚未产生；极端情况被迟到回包污染由 seq 校验兜底（见下）。

```cpp
// 伪代码（v1.3 修正：锁作用域 / 回包电平化 / seq 不匹配重试 / 等待掩码）
{
  std::lock_guard<std::mutex> lock(mutex_);       // ← 锁作用域收窄：只覆盖槽重置与写请求
  Ensure();
  reply_hdr->reply_pending = 0; reply_hdr->seq = 0; reply_hdr->length = 0;
  sync_depth_.fetch_add(1);                       // 必须在写请求之前
  写 per-pid 请求通道（置 pending 标志）+ SetEvent(req_evt);
}                                                 // ← 等待期间不持锁：嵌套 Send 重入不再自死锁

for (;;) {
  // wake mask = 0：渲染阻塞栈内不派发任何窗口消息，防 CEF 内部 SendMessage 重入（v1.3 明确）
  DWORD w = MsgWaitForMultipleObjects({reply_event_, handoff_event_},
                                      FALSE, remaining_timeout(), 0);
  if (w == reply_event 醒) {
    if (reply_hdr->reply_pending && reply_hdr->seq == seq) {   // 电平 + seq 双校验
      读回包; reply_hdr->reply_pending = 0; break;
    }
    continue;   // seq 不匹配（迟到回包唤醒了本次调用）：丢弃，用剩余超时继续等
  }
  if (w == handoff_event 醒) {
    drain handoff 队列 → 逐个【重入执行】JS 回调
      （Enter 回调自身 context + TryCatch，见 §6.2.3）
      → FromV8(retval) 写 event_result 回请求通道
    → 继续循环等外层回包;
  }
  if (超时) → 错误 "sync jsapi call timed out";
}
if (sync_depth_.fetch_sub(1) == 1) {          // 最外层退出
  drain handoff 队列残留 → 迟到的同步事件按普通异步事件 PostTask 补发;
  drain stash  队列     → 逐个 CefPostTask 派发;
}
```

嵌套调用的正确性依据：渲染进程只有主线程一个执行者，任一时刻只处于一个等待层级，auto-reset event 每次只唤醒当前层；回包以 `reply_pending` 电平 + seq 双校验——迟到回包（上一轮超时调用的残留）唤醒下一次调用时 seq 不匹配 → 丢弃并用剩余超时继续等，不错拿、不误报（v1.3 修正：原设计纯信号驱动 + seq 不匹配即报错，在 at-least-once 语义下会让下一次调用无谓失败）。

**竞争窗口分析**（两个方向都收敛到正确语义）：

- `0→1` 瞬间 watcher 读到 0 走 PostTask：任务在消息循环执行，等效暂存，无害；
- `1→0` 瞬间 watcher 读到 1 走 stash：随后 Send 退出时 drain，无害。

#### 6.2.3 HandleEvent 补齐返回值

`ExecuteFunction` 的返回值当前被丢弃，改为：同步事件（invoke_id > 0）时 `FromV8(retval)` 写回执到请求通道。

**v1.3 补充 — 重入执行的 V8 细节**：

- **context 配对**：handoff 重入执行时必须 Enter 该回调自己的 context（回调可能属于不同 frame/context），执行完配对 Exit——不能复用外层调用者的 context；
- **异常捕获**：`ExecuteFunction` 以 `CefV8TryCatch` 包裹并检查 `HasException()`，回调抛出的 JS 异常转成 `event_result` 的 error 字段送回 C++（`DispatchEventSync` 返回 Null + 错误串），**不允许异常穿透到外层 C++ 调用栈**；
- 返回值序列化失败（如返回函数/代理对象）按错误处理，不静默。

### 6.3 Browser 侧改造（`src/bridge/jsapi_browser_bridge.cpp`）

#### 6.3.1 通道读取器：读/执行分离 + 嵌套路由（v1.1 重设计）

每个渲染进程的请求通道配一个**读取器**：线程池 `RegisterWaitForSingleObject` 注册等待（规避 `WaitForMultipleObjects` 64 句柄上限，页面数自动扩展；规模化可选 IOCP 完成端口）。读取器是 `req_evt_<pid>` 的**唯一等待者**，且**永远不因执行而停止等待**：

```
读取器（每 pid 一个）：
  等 req_evt_<pid> 唤醒（电平触发：pending 标志 + 互斥量内读取）→
    op == event_result：
      查 invoke 表 → 命中：填结果 + SetEvent(nest_evt)（会话中）/ 直接完成（无会话）
                    未命中：丢弃 + 日志（迟到的回执）
    op == rpc 且 execute_level(X) == 0：      // 顶层请求
      QueuedConnection 投递 GUI 任务 { BeginLevel(X); Process; 写回包; EndLevel(X) }
      读取器立即回到等待                      ← 读/执行分离，阻塞点②解除
    op == rpc 且 execute_level(X) > 0：       // 嵌套请求（该 pid 会话进行中）
      压入嵌套队列(X) + SetEvent(nest_evt_X)  // 转交 GUI 内联等待循环
      读取器立即回到等待
```

**嵌套请求为何必然落在会话期间**：渲染进程单写者——只有在收到同步事件（GUI 侧 DispatchEventSync 推送、处于内联等待循环中）后才会发出嵌套请求；此时 `execute_level > 0` 恒成立。超时后迟到的嵌套请求处理见 §10.2。

**多页面并发语义**：请求通道按 PID 隔离消除单槽竞态；GUI 单线程会话串行（WPS 同款）——页面 A 长会话期间，页面 B 的顶层请求照常被各自读取器接收、投递 GUI 队列，**等会话结束后执行**。页面间排队但不丢请求、不因竞态超时。

**v1.3 修正 — 读取器不得触碰 CEF 线程亲和 API**：现状 `ResolveEnvById` 在工作线程调用 `CefBrowserHost::GetBrowserByIdentifier` / `GetFrameByIdentifier`（代码注释自承需 UI 线程），且找不到 browser 时回退 claimed env——"防伪造 env"实际无效。改为：握手 hello 携带 browser_id/frame_id，browser 侧登记 **pid→env 纯数据映射表**，读取器只查表校验，不调任何 CEF API；映射表随 `OnBeforeClose` / `OnRenderProcessTerminated` 维护。

**v1.3 修正 — 必须新增非阻塞投递接口 `SetMainThreadPoster`**：`SetMainThreadDispatcher` 现约定为**阻塞式**（返回时 task 已完成，`docs/构建与调试.md` 已写成契约，Qt 宿主用 `BlockingQueuedConnection` 实现）。读取器若用它投递 GUI 任务，则退回"读/执行不分离"，阻塞点②复活。修正：新增 `SetMainThreadPoster`（异步，投递即返回，Qt 宿主用 `QueuedConnection` 实现），读取器顶层请求一律走 Poster；`RunOnMainThread`（阻塞）保留给异步 RPC 等存量路径。**Poster 未设置时：读取器退化为同步执行模式（仅支持顶层请求，嵌套路由不可用）+ 日志告警**——这是 Phase 2 的硬前置。

**IOCP 口径（v1.3 明确）**：主选 `RegisterWaitForSingleObject`（命名事件句柄原生兼容、页面数自动扩展、规避 64 句柄上限）；IOCP 仅作规模化备选——命名事件句柄**不原生兼容** IOCP，需先完成"命名管道化"通道改造，不在本方案范围。

#### 6.3.2 事件派发统一走共享内存通道

`OnEvent`（异步）不再 `CefPostTask(TID_UI)` + `SendProcessMessage`，改为：按 listener env 查 evt 通道 → 写环形缓冲 → `SetEvent`。`EventDispatchTask` 整个删除，`jsapi.event` 进程消息主路径退役（仅保留作异步事件单条超限 >1MB 的回退通道，见 §10.3-4，v1.3）。

**额外收益**：事件派发摆脱 CEF UI 线程依赖，插件工作线程直接写 shm，延迟更低。

**env→evt 通道映射**：由引导握手登记（见 §6.5）。

#### 6.3.3 OnEventSync：内联等待循环（v1.1 核心修订，弃 QEventLoop）

复刻 WPS `WaitLevelFinish` 模式：嵌套请求**不进 Qt 消息队列**，由等待循环被 `nest_evt` 唤醒后**就地内联执行**——当前线程就是 GUI 线程，插件函数的 Qt 控件亲和天然满足，且完全不泵 posted 消息：

```cpp
JsValue OnEventSync(event, callback_id, target, args, timeout_ms, error) {
  // 对齐校验：会话深度与执行深度不齐 → 拒绝同步嵌套（防半截重入乱序死锁）
  if (execute_level_ != nest_level_) {
    *error = "level misaligned, sync nesting rejected";
    return JsValue::Null();
  }
  BeginLevel();                          // execute_level_++，写入共享内存（渲染侧可读）
  nest_evt_.DrainQueueOnEnter();         // 清掉可能滞留的迟到项
  invoke_id = NextInvokeId();
  if (!写 evt 环形缓冲(带 invoke_id) || !SetEvent(evt_event)) {
    EndLevel();
    *error = "event channel overflow";
    return JsValue::Null();
  }

  // 内联等待循环：WPS 式 —— 事件优先、只派发 sent、不进 Qt 事件循环
  bool done = false, timed_out = false;
  for (;;) {
    DWORD w = MsgWaitForMultipleObjects(
        /*hEvents*/{nest_evt_.handle(), abandon_.handle()},
        FALSE, 200 /*切片*/, QS_SENDMESSAGE);
    if (w == WAIT_OBJECT_0 + 2) {        // 渲染进程异常退出
      *error = "render process abandoned";
      break;
    }
    if (w == WAIT_OBJECT_0 + 1 || w == WAIT_OBJECT_0) {   // 嵌套通知（消息醒来时补查）
      if (w == WAIT_OBJECT_0 + 1) {
        DWORD noWait = WaitForSingleObject(nest_evt_.handle(), 0);
        if (noWait == WAIT_OBJECT_0) w = WAIT_OBJECT_0;   // 事件优先，防消息占用循环
      }
      while (auto item = nest_evt_.Pop()) {
        if (item.op == event_result) {
          if (item.invoke_id == invoke_id) { result = item.value; done = true; }
          else CompleteOtherInvoke(item);                 // 迟到回执：查表完成或丢弃
        } else {
          // 嵌套 RPC 请求：对齐校验通过后就地内联执行
          if (execute_level_ != nest_level_ + 1) { 回错误包; continue; }
          nest_level_++;                                  // StartNestLevel
          写回包( rpc_.Process(item.request) );           // ★ 就地执行，当前即 GUI 线程
          nest_level_--;                                  // EndNestLevel
        }
      }
    }
    if (w == WAIT_OBJECT_0 + 2 || w == WAIT_TIMEOUT) { /* 超时切片 */ }
    if (done || 超过 timeout_ms) { timed_out = !done; break; }
    if (w == WAIT_OBJECT_0 + 2 + 0 && HasSentMessage()) {
      // 只派发 sent（PeekMessage 触发内部处理），不取 posted —— 防跨线程 SendMessage 阻塞，
      // 也不进 Qt 事件循环（点按钮、再调 JSAPI、重入死锁）
      MSG msg; ::PeekMessage(&msg, NULL, 0, 0, PM_NOREMOVE);
    }
  }
  EndLevel();                              // execute_level_--
  if (timed_out) { *error = "sync event timed out"; return JsValue::Null(); }
  return result;
}
```

要点：

- **双门等待**：`nest_evt`（嵌套请求/回执到达）与 `abandon`（渲染进程退出），加 `QS_SENDMESSAGE` 守卫（WPS 同款：事件优先补查 + 只派发 sent）；
- **内联执行**：嵌套 `rpc_.Process` 在等待循环里直接调用，不投递、不排队、不泵 posted——阻塞点③解除且**无 Qt 重入**（v1.0 的 QEventLoop 方案及其风险整体删除）；
- **等待循环兼作嵌套执行泵**：这是 WPS 能"不泵 posted 也安全"的根本原因，v1.1 完整复刻；
- 每层同步事件一个等待循环，天然支持多层嵌套（深度受 §9 边界约束）；
- **v1.3 硬前置**：本循环假设"当前线程即宿主 GUI 线程"——仅当宿主已设置 Poster/Dispatcher（执行被投递到宿主 UI 线程）时成立。未设置时执行落在读取器线程，而读取器是 `req_evt_<pid>` 的唯一等待者，一进等待循环嵌套请求即无人读取 → 必然超时。因此 **Phase 2 起"宿主已设置 Poster"为硬前置**（启动时断言；未设置则禁用同步嵌套能力，仅保留顶层请求）。
>
> v2.0 修订：读取线程与会话线程分离后，等待循环跑在会话线程，读取线程始终空闲收请求，上述前提由"执行必须在 GUI 线程"解除为"执行不得占用读取线程"；Poster 仍保留为宿主声明支持同步事件的能力开关（见 §14.1-5）。

#### 6.3.4 process_mutex_ 条件退役（v1.3 修正）

> v2.0 已改为"会话线程 + 函数级亲和"，`process_mutex_` 被直接删除，本节仅保留设计推导过程；结论见 §14.1-4。

原方案"直接移除"的前提不成立：`RunOnMainThread` 在未设置 dispatcher 时直接在收取请求的线程执行 `task()`（`jsapi_browser_bridge.cpp:128-140`）——同步请求在读取器线程、异步请求在 CEF UI 线程并发跑 `rpc_.Process`，此时移锁即数据竞争。

修正为**条件退役**：

- 宿主已设置 Poster/Dispatcher（Phase 2 硬前置）：所有 `Process` 均在宿主 GUI 线程单线程串行，`process_mutex_` 移除；`JsRegistry` 内部锁均为短作用域（不跨用户回调持有），同线程重入安全；
- 未设置（兼容降级模式）：`process_mutex_` 保留并改为 `std::recursive_mutex`（嵌套内联执行同线程重入不死锁），仅支持顶层请求。

#### 6.3.5 双计数器与对齐校验（v1.1 新增，仿 WPS ExecuteLevel/NestLevel）

| | execute_level | nest_level |
|---|---|---|
| 范围 | 跨进程：写入共享内存，渲染侧可读 | 仅 browser 进程内 |
| +1 时机 | BeginLevel()：顶层 GUI 任务进入 / DispatchEventSync 推嵌套帧 | Process 执行入口（含内联嵌套执行） |
| -1 时机 | EndLevel()：对应会话/帧结束 | Process 返回 |
| 用途 | 标识"第几层同步会话"；读取器据此区分顶层/嵌套路由 | 标识 GUI 线程实际执行到第几层 API |

**对齐校验规则**（栈不齐即拒绝，防半截重入乱序死锁）：

- `DispatchEventSync` 入口：`execute_level == nest_level` 才允许推嵌套帧（随后 execute_level+1）；
- 内联执行嵌套请求前：`execute_level == nest_level + 1` 才允许（有一层已声明未执行的帧；执行期间 nest_level 追平）；
- 不满足 → 拒绝：同步事件返回 `"level misaligned"`，嵌套请求回错误包。

计数器增减不因"同层连续多次 RPC"变化——同层复用，深度只反映真实嵌套栈。

### 6.4 插件 API 扩展

```cpp
// JsObjectBase 新增
// 同步事件：单播定向派发，阻塞直到目标页面回调返回或超时。
// error 为空 → 成功，返回回调返回值；
// error 非空 → 失败，返回 Null，错误串区分原因：
//   "no listener for event 'xxx'"          无监听者
//   "sync event timed out after Nms"       超时（回调可能迟到执行，见 §10.1）
//   "nested event depth exceeded"          深度超限
//   "event channel overflow"               事件环形缓冲写满
//   "level misaligned, sync nesting rejected"  栈对齐校验失败
//   "sync event callback threw exception"      回调抛 JS 异常（TryCatch 捕获，见 §6.2.3）
//   "sync events not supported by this sink"   sink 未实现 OnEventSync（默认实现返回，v1.4）
JsValue DispatchEventSync(const std::string& event,
                          const RpcEnv& target,
                          const std::vector<JsValue>& args,
                          int timeout_ms = 10000,
                          std::string* error = nullptr);
```

`BroadcastEvent` / `DispatchEvent`（异步）签名与语义完全不变。

**同步事件仅支持单播，且明确"首个匹配 listener"语义（v1.3 修正）**：现状 `EmitTo`（`src/core/js_object.cpp:161-189`）对每个匹配 listener 各调一次 `OnEvent`，而 `DispatchEventSync(event, target, args)` 只有 env 没有 callback_id——同一 env 同一事件注册多个回调时"返回值取谁"未定义，"target 有效"并不保证唯一。修正：

- `EmitTo` 新增单播路径：过滤后取**首个匹配 listener**（= `listeners_` 注册顺序首个，vector 顺序稳定，v1.4 明确）执行并取其返回值，其余不执行；
- sink 单播接口返回**命中数**（0 = `no listener`，立即报错返回，不白等 10s 超时）；
- 多播需求一律走 `BroadcastEvent`（异步，语义不变）。

**`JsEventSink::OnEventSync` 提供默认实现而非纯虚（v1.4）**：默认立即返回 Null + `"sync events not supported by this sink"`，不同步等待、不阻塞——与"无监听者立即报错"口径一致。收益：存量 sink（`tests/self_test.cpp` 的 TestEventSink、宿主自定义 sink）**零改动编译通过**，不关心同步事件的实现方无需被迫适配；browser bridge 提供正式实现。

### 6.5 请求通道隔离与两端对齐（v1.5：按 browser_id 对齐，取消引导握手）

> **v1.5 修订**：本节描述的 hello / hello_ack 引导握手已在落地后废弃（白屏回归根因，详见 §14.4）。
> 现行实现：通道 key = `browser_id`，浏览器进程在 `OnAfterCreated` 建通道并启动读取线程，
> 渲染进程在 `OnContextCreated` 用 `frame->GetBrowser()->GetIdentifier()` 得到同一个 key 后 Ensure 同名对象，
> 两端无需任何进程消息即可对齐；env 直接由浏览器侧在 `OnAfterCreated` 写入。
> 下方"引导握手"小节保留为设计演进记录。

**背景**：v1.0 保留的全局单槽请求通道存在多页面丢请求竞态（§2.2）。WPS Web2 的印证：请求通道按 renderPid 组织（`m_pJsApiIpcs`、`m_hMainEvents`），并用 ProcessMessage 两段式确定会话归属后才传 RPC。

**通道命名**：见 §6.1.1，全部带 `<pid>` 后缀。全局 `Local\jsapi_req` 系列命名对象退役。

**引导握手**（复用 WPS 两段式的第一段思想——先定会话归属，再传调用）：

```
Renderer OnContextCreated（此时主线程未阻塞，进程消息可用）：
  SendProcessMessage(PID_BROWSER, "jsapi.channel.hello",
                     { pid, browser_id, frame_id,
                       req_map, req_evt, reply_map, reply_evt, evt_map, evt_evt })

Browser OnProcessMessageReceived：
  按 pid 打开各通道句柄、登记 pid → (env, 通道) 纯数据映射（不调 CEF API）
  创建进程内 nest_evt / abandon 事件
  RegisterWaitForSingleObject 注册该 pid 请求通道的读取器
  回 hello_ack（renderer 以此作为"通道就绪"标志）
```

**握手启动竞态处理（v1.3 补）**：页面可能在 `onload` 里立刻发起同步调用，若请求先于读取器注册到达 → 无人等 → 10s 超时。处理：`Send` 入口检查 `channel_ready_`（收到 hello_ack 置位）——未就绪时短轮询等待（如 50ms × 20 次，仍失败则报"channel not ready"明确错误而非笼统超时）。hello 在 OnContextCreated（主线程未阻塞）发出，正常时序下 ack 先于任何页面 JS 执行到达。**子 frame 不建 root、不支持同步调用**（现状即如此，`OnContextCreated` 仅主 frame 建 root），hello 仅覆盖主 frame。

**清理三件套**（WPS 同款；v1.3 修正按 pid 精确清理）：

- `OnBeforeClose`：该浏览器关闭时清理其 env 映射；渲染进程已无存活浏览器 → 注销读取器、关闭该 pid 通道句柄；
- `OnRenderProcessTerminated`：触发 `abandon_<pid>` → GUI 内联等待循环立即退出（不等超时）、读取器注销。**现状 `QtHostClient` 未实现该回调（仅有 `OnBeforeClose`）——改造清单含补 `CefRequestHandler::OnRenderProcessTerminated` 并接线 bridge**，否则杀渲染进程只能等 10s 超时；
- 回包通道：**修复现状 `CloseReplyChannels()` 无条件 clear 全部的缺陷（v1.3）**——多浏览器场景关一个页面会掐掉所有页面的回包通道。改为按 pid/map_name 精确清理，懒加载打开语义保留。

## 七、完整时序闭环走查

```
[Renderer主线程]  funcxxx() ─写请求(seq=N, 通道X)→ 阻塞 MsgWait{reply, handoff}
[读取器X]         醒于 req_evt_X → pending 置否 → op=rpc, execute_level(X)==0 → 顶层:
                  投递 GUI 任务{BeginLevel(X)→1; Process(N); 写回包; EndLevel→0} → 回到等待
[Qt GUI线程]      任务执行 → Process(N)（nest_level→1）→ funcxxx → DispatchEventSync
                   对齐校验 execute_level(1)==nest_level(1) ✓
                   → BeginLevel→2 → invoke_id=1 → 写 evt 环形缓冲 → SetEvent(evt_event)
                   → 进入内联等待循环 MsgWait{nest_evt_X, abandon, QS_SENDMESSAGE}
[Renderer watcher] 醒于 evt_event → 读事件 invoke_id>0 → handoff 队列 + SetEvent(handoff)
[Renderer主线程]  醒于 handoff → 重入执行 JS 回调
                   → funcxxx2() ─写请求(seq=N+1, 通道X)→ 阻塞 MsgWait            ← 阻塞点①解除
[读取器X]         醒于 req_evt_X → op=rpc, execute_level(X)==2>0 → 嵌套路由:
                  压入嵌套队列(X) + SetEvent(nest_evt_X) → 回到等待               ← 阻塞点②解除
[Qt GUI线程]      醒于 nest_evt_X → pop → 对齐校验 execute_level(2)==nest_level(1)+1 ✓
                   → nest_level→2 → 【就地内联】Process(N+1) → 写回包(N+1) → nest_level→1
                                                                         ← 阻塞点③解除（无 Qt 重入）
[Renderer主线程]  嵌套 Send 醒 → funcxxx2 结果返回 JS → 回调 return retval
                   → 写 event_result(invoke_id=1, 通道X) → 继续等 seq=N
[读取器X]         醒于 req_evt_X → op=event_result → 查表命中 invoke_id=1
                   → 填结果 + SetEvent(nest_evt_X) → 回到等待
[Qt GUI线程]      醒于 nest_evt_X → pop → invoke 完成 → 退出等待循环
                   → EndLevel→1 → DispatchEventSync 返回 JsValue → funcxxx 继续
                   → Process(N) 完成（nest_level→0）→ 写回包(N) → EndLevel→0
[Renderer主线程]  外层 Send 醒 → funcxxx 返回值交给 JS ✓
```

全链路无循环等待；嵌套执行全程不进 Qt 事件循环。

## 八、最终语义总表

| 场景 | 行为 |
|------|------|
| 同步 RPC 内发同步事件（定向单播） | 嵌套栈重入执行回调，C++ 拿到返回值 |
| 同步 RPC 内发异步事件 | 暂存 stash 队列，最外层调用返回后按序派发 |
| 异步 RPC 内发同步事件（v1.3 补） | watcher 第四路 PostTask 派发回调、回执走请求通道；GUI 内联等待循环照常完成 invoke |
| 正常状态发异步事件 | watcher 线程 PostTask 立即派发 |
| 同步事件超时 | 返回错误；回调可能迟到补发（at-least-once） |
| 同步事件无监听者 | 返回错误，不阻塞 |
| 嵌套深度超限 | 抛 JS 异常 / 返回错误，不死锁 |
| 栈对齐校验失败 | 同步嵌套被拒（`level misaligned`），防半截重入死锁 |
| 多页面同时同步调用 | 请求通道按 PID 隔离无竞态；执行按会话串行（页面间排队，不丢请求） |
| 广播事件 | 仅异步（BroadcastEvent），语义不变 |

## 九、保护边界

| 边界 | 位置 | 上限/默认 | 超限行为 |
|------|------|-----------|----------|
| 渲染侧 Send 重入深度 | SyncChannel | 8 层 | 抛 JS 异常 `nested call depth exceeded` |
| Browser 侧 Process 嵌套深度（nest_level） | bridge | 8 层 | 直接回错误包 |
| 内联等待循环嵌套深度（execute_level） | bridge | 8 层 | 返回 Null + 错误 `"nested event depth exceeded"` |

| 每层等待超时 | Send / OnEventSync | 10s（OnEventSync 可参数化） | 超时错误 / 返回 Null |
| 渲染进程异常退出 | abandon 事件 | — | 等待循环立即退出，不等超时 |

## 十、已知风险与语义变化

### 10.1 需插件作者知悉的语义

**DispatchEventSync 超时后，前端回调仍可能被派发（at-least-once）**：迟到的同步事件在渲染侧 Send 退出时按普通异步事件补发，其回执到达 browser 时 invoke 表项已删除，静默丢弃 + 日志。插件不得假设"超时 = 回调一定没执行"。

### 10.2 迟到嵌套请求的兜底路径

`DispatchEventSync` 超时、GUI 已退出等待循环后，渲染侧已在途的嵌套请求（funcxxx2）到达读取器：

- 会话仍活跃（execute_level > 0）→ 进嵌套队列滞留：funcxxx 再次进入等待循环时被入口 drain 执行，或会话结束时（见下）转出；
- 会话结束（EndLevel→0）→ **会话收尾时 drain 嵌套队列，残留请求转顶层 GUI 任务排队执行**——回包可能延迟到达，渲染侧 10s 超时语义兜底。

两条路径都保证嵌套请求**最终被执行且回包**，不静默丢弃。

### 10.3 风险清单

1. **会话期间 GUI 线程不泵 posted 消息**（v1.1 以此换取无 Qt 重入）：其他子系统经 QueuedConnection 投给 GUI 线程的任务、用户输入、定时器在会话期间排队等待。宿主其他模块需知悉"JSAPI 同步事件派发具有模态性"；跨线程 `SendMessage` 到 GUI 线程仍会被及时处理（QS_SENDMESSAGE 守卫 + PeekMessage 派发 sent），不会阻塞发送方。**v1.0 的 QEventLoop 重入风险（原最大风险）已整体消除**。
2. **页面间会话串行**：页面 A 的长会话期间，页面 B 的同步调用排队（不丢、不竞态超时，但延迟取决于 A 的会话时长）。与 WPS 主线程单会话模型一致；这是"所有 JSAPI 函数在 UI 主线程执行"前提下的固有代价，**根治路径见 §13（v2.0 Apartment 会话线程模型）**。
3. **异步事件暂存积压**：长同步调用期间异步事件积压在 stash 队列（进程内存，不占环形缓冲槽位），外层返回后按序派发。可加上限告警。
4. **环形缓冲溢出**：同步事件满即失败（不丢）；异步事件单条超限（>1MB）回退 `kEventMessage` 进程消息（兼容现状无上限语义，v1.3 修正），槽满仍丢弃 + 计数告警。
5. **迟到回执**：invoke 表项已删除时到达的 event_result 静默丢弃 + 日志，不视为错误。
6. **异步 RPC + 同步事件拉长 GUI 模态时长（v1.3 新增）**：异步 RPC 的执行经阻塞式 dispatcher 落在 GUI 线程，其内部的 DispatchEventSync 同样进入内联等待循环——"异步调用"在此期间对宿主 UI 具备模态性。规避：该类节点声明 Worker 亲和（§13），或改用 BroadcastEvent + 二次调用取结果。

## 十三、v2.0 演进方向：Apartment 会话线程模型

> 状态：**已按函数级亲和 + 默认 Worker 实施**（与下文"节点级 + 默认 UIThread"的原始设计不同，见 §13.3 实施修订）。解决 v1.1 的固有局限（§10.3-1 UI 模态、§10.3-2 页面间会话串行）：多 web 页并发嵌套同步调用时，UI 主线程不冻结、页面互不排队。

### 13.1 动机与核心洞察

v1.1（与 WPS 同类）的正确性基线是"**所有 JSAPI 函数在 UI 主线程执行 + 等待也在 UI 主线程**"。由此推出两个不可消除的代价：

- 等待占用 UI 线程 → 会话期间宿主 UI 模态冻结；
- 单执行线程 → 多页会话只能串行，B 页等 A 页。

核心洞察：**UI 主线程真正需要的只是"执行函数体"，"等前端回调"根本不需要占用 UI 线程**。把两者拆开，是唯一出路（"多页 UI 亲和函数真并发"因 Qt 控件非线程安全在原理上不存在，只能做到"等待移出 UI 线程 + 会话并行交错"）。

### 13.2 线程模型

```
                    ┌── 会话线程 A（渲染进程 A 专属）────────────────┐
读取器A ─顶层请求──▶ │  执行 Worker 亲和的 funcxxx                     │
                    │  DispatchEventSync 等待发生在这里               │
                    │  （纯事件等待，非 QEventLoop）                   │
                    │  嵌套请求经 nest_evt 路由到这里，就地内联执行    │
                    └──────────────┬─────────────────────────────────┘
                                   │ UIThread 亲和函数体 / 显式 UI 片段
                                   ▼（BlockingQueuedConnection，短平快）
                    ┌── UI 主线程 ──────────────────────────────────┐
                    │  只执行函数体片段，绝不等前端回调                │
                    │  单片段毫秒级，多会话排队无感                    │
                    └───────────────────────────────────────────────┘
                    ┌── 会话线程 B（渲染进程 B 专属）────────────────┐
读取器B ─顶层请求──▶ │  ……与 A 完全独立，真并行                        │
                    └───────────────────────────────────────────────┘
```

- **会话线程**：每渲染进程一个，随引导握手创建、abandon/清理时退出。顶层请求由读取器投递到**该 pid 的会话线程**（替代 v1.1 的 GUI 全局队列）；
- **UI 主线程**：退化为纯执行器——只跑 UIThread 亲和的函数体和 Worker 内显式投递的 UI 片段，永不进入等待前端的状态 → **UI 永不模态**；
- **多页并行**：每页一个会话线程，嵌套会话互不排队。

### 13.3 线程亲和声明（实施修订：函数级 + 默认 Worker）

原设计为**节点级 + 默认 UIThread**（兼容存量插件）。实际实施改为**函数级 + 默认 Worker**：本项目没有存量插件，且"操作 Qt 控件"只集中在少数成员上，函数级粒度更贴合使用方式。

```cpp
// 默认 Worker：留在该页面的会话线程执行。
table.Function("readFile", jsapi::JsType::String, {{"path", jsapi::JsType::String}},
               ReadFileImpl);

// 显式 UI 亲和：会话线程经宿主 dispatcher 阻塞切到 UI 线程执行。
table.Function("setWindowTitle", jsapi::JsType::Bool,
               {{"title", jsapi::JsType::String}}, SetTitleImpl,
               /*async=*/false, jsapi::ThreadAffinity::UI);

// 属性同样支持亲和参数（getter, setter, affinity）。
table.Property("uiState", jsapi::JsType::Int, GetUiState, nullptr,
               jsapi::ThreadAffinity::UI);
```

函数级亲和的已知代价（§13.7-1 的推论）：同一节点内 UI 成员与 Worker 成员操作同一份成员状态时需插件自行同步；跨页面调用同一节点也会并发。

### 13.4 关键规则

| # | 规则 | 原因 |
|---|------|------|
| 1 | **UIThread 亲和函数内禁止 DispatchEventSync**：运行时返回错误 `"sync event not allowed in UI-affine API"`，建议改用异步 BroadcastEvent | 否则等待回到 UI 线程，模态复辟 |
| 2 | Worker 函数体内访问 UI 必须 `RunOnUIThread` 显式投递，片段内禁止任何等待前端的调用 | 保证 UI 线程只执行不等待 |
| 3 | 嵌套请求的执行线程跟随外层会话线程（nest_evt 路由到会话线程）；若嵌套调用的目标是 UIThread 亲和节点 → 会话线程经 BlockingQueuedConnection 投 UI 执行函数体后取回结果 | UI 片段毫秒级，排队无感 |
| 4 | 双计数器语义调整：execute_level 不变（跨进程）；nest_level 变为 **per-会话线程**计数，对齐校验在各自会话内进行 | 会话并行后无全局单一栈 |
| 5 | 会话线程的等待循环不需要 QS_SENDMESSAGE 守卫（无窗口、不收跨线程 SendMessage），纯 `WaitForMultipleObjects{nest_evt, abandon}` | 简化；UI 线程不再有长等待循环 |

### 13.5 与 v1.1 的差异

| 维度 | v1.1 | v2.0（本章） |
|------|------|--------------|
| 顶层请求去向 | GUI 全局任务队列（页面间排队） | 该 pid 会话线程（页面间并行） |
| DispatchEventSync 等待位置 | UI 主线程内联等待循环 | 会话线程等待循环 |
| UI 主线程职责 | 执行 + 等待（模态） | 只执行短片段（永不模态） |
| 嵌套路由终点 | GUI 等待循环 | 会话线程等待循环 |
| 插件线程亲和 | 隐式全 UIThread | 函数级显式声明，默认 Worker |
| 多页并发嵌套 | 串行 + 有界超时 | 真并行 |
| UI 片段访问 | 不需要（全在 UI 线程） | `RunOnUIThread` 显式投递 |

通道协议、事件环形缓冲、watcher/handoff/stash、event_result、引导握手、abandon 清理等基础设施**全部复用 v1.1**，不动。

### 13.6 迁移路径

1. **先落地 v1.1**（Phase 1–4），获得正确性基线与全部通道基础设施；
2. **一步到位**：没有存量插件，直接以"函数级亲和 + 默认 Worker"上线，跳过"默认 UIThread 过渡期"；
3. **标注例外**：只有必须操作 Qt 控件的成员（`uiInfo` / `setWindowTitle` / `showStatus` / `openDialog`）声明 `ThreadAffinity::UI`，其余成员保持默认；
4. **后续**：如出现多会话线程共享状态的节点，优先内部加锁；确有需要再考虑节点级亲和声明。

### 13.7 风险

1. **Worker 节点的状态并发**：多会话线程并发调用不同 Worker 节点，若业务节点间共享状态需自行加锁；节点级亲和保证单节点内部串行（同一会话线程内嵌套串行 + 跨页对该节点的调用在各自会话线程并发——**注意：跨页调用同一 Worker 节点仍会并发**，需要锁的节点应留在 UIThread 或内部加锁）；
2. **UIThread 禁同步事件的约束是运行时的**：无法编译期强制，依赖文档与 code review；
3. **RunOnUIThread 滥用**：片段内若调用长阻塞操作（模态对话框等）会退化 UI 响应性，需约定片段时长预算；
4. BlockingQueuedConnection 死锁面：会话线程持锁上 UI、UI 又反向等该会话线程的典型死锁需在文档中列为编码禁例。

## 十四、实现落地记录（v1.4 → 代码）

### 14.1 与方案的实现级偏差（均已验证）

1. **通道代码独立成模块**：新增 `include/jsapi_bridge/jsapi_channel.h` + `src/bridge/jsapi_channel.cpp`，只依赖 Win32 与 jsapi_core，不依赖 CEF/Qt；`jsapi_bridge` 与 `jsapi_self_test` 共用，通道语义可被自测直接覆盖。
2. **读取器改为每浏览器（通道）一个常驻线程**：方案 §6.3.1 用 `RegisterWaitForSingleObject` 线程池。落地改为普通 `std::thread`，等待 `{req_evt_<key>, abandon_evt, stop_evt}`。原因：关闭时可确定性地 join，避免 `UnregisterWaitEx(INVALID_HANDLE_VALUE)` 与宿主阻塞式投递互相等待；"每个 key 唯一读取者"这一关键不变量不变。v1.6 起同一渲染进程可同时持有多个 key（每浏览器一条通道）。
3. **握手不做 `channel_ready_` 硬门禁**：`OnContextCreated` 里的首个 describe 本身就是同步 RPC，等待 hello_ack 会自死锁（ack 只能在本回调返回后由消息循环投递）。落地依赖 pending 电平 + 读取器注册后立即补查，竞态已被消除；`channel_ready_` 仅作诊断与日志。
4. **`process_mutex_` 已删除**（v2.0 函数级亲和改造）：顶层请求在各页面会话线程执行，全局锁会让页面间互相排队；若锁跨函数体持有，"Worker 顶层 → 嵌套 UI 成员 → UI 函数体内再发同步事件"会形成跨线程死锁。安全性改由 `JsRegistry` 内部锁 + `JsObjectBase` 函数表锁保证，跨页共享的节点状态由插件自行同步。
5. **读取器与会话线程分离**（v2.0）：读取线程只收与路由，顶层请求交会话线程执行；两者合一会在插件派发同步事件时饿死嵌套请求（读取线程被等待循环占住），违反 §6.3.3 的前提。
6. **异步事件回退**：环形缓冲写失败（单条超槽容量或槽满）时回退 `jsapi.event` 进程消息；同步事件写失败直接报 `event channel overflow or event too large`，不静默丢弃。

### 14.2 新增测试（`tests/self_test.cpp`，全部通过）

- 同步事件单播：同 env 注册两个监听者，只执行注册顺序首个；无监听者立即返回 `no listener`，不白等超时。
- 多层嵌套：同步事件回调里先重入 `RpcHost::Process`，再发起下一层 `DispatchEventSync`，4 层展开结果与调用次数均符合预期。
- 兼容性：未实现 `OnEventSync` 的存量 sink 走默认实现，返回 `sync events not supported by this sink`，不破坏编译与行为。
- 通道单测：请求 pending 电平只消费一次；回包 seq 不匹配不消费、迟到回包可被后续正确回包覆盖；事件环形缓冲 FIFO/invoke_id 透传/槽满拒绝；payload 与回执编解码 roundtrip；通道名按 key（v1.5 起为 browser_id）隔离。

### 14.4 白屏回归修复（v1.5）：弃用引导握手，通道按 browser_id 对齐

**现象**：`jsapi_qt_host.exe` 启动后白屏，约 10s 后才渲染，且 `window.Extention` 始终为 `undefined`。

**定位证据**（渲染进程侧落盘日志 + 浏览器 UI 线程心跳）：UI 线程心跳全程未断（浏览器 UI 不被阻塞），
但 `jsapi.channel.hello` 直到渲染主线程从 `Send` 的 10s 超时返回后才被浏览器收到（时间戳完全对齐）。

**根因**：`OnContextCreated` 里首个 describe 是同步 RPC，会把渲染主线程阻塞在
`MsgWaitForMultipleObjects(..., wake mask = 0)`；**渲染主线程阻塞期间，渲染→浏览器的进程消息发不出去**。
而 v1.1 的设计要求浏览器先收到 hello 才建立通道、启动读取线程——握手消息与首个同步请求互为前置，形成死锁，
最终表现为"首个 describe 超时失败 → 无 `Extention`"，同时文档解析也被推迟到超时之后。

**修复（已落地）**：

1. **通道 key 改为 browser_id**：`Local\jsapi_*_<key>` 的 key 取浏览器标识。浏览器进程在
   `OnAfterCreated` 就能得到它（并直接建通道 + 起读取线程），渲染进程在 `OnContextCreated` 用
   `frame->GetBrowser()->GetIdentifier()` 得到同一个值，**两端各自 Ensure，无需任何进程消息握手**；
   同一浏览器的后续导航（含渲染进程崩溃重载）沿用同名对象，读取线程不必重建。
2. **删除 `jsapi.channel.hello` / `hello_ack`**：env（browser_id / frame_id）在 `OnAfterCreated` 直接落进通道状态；
   `FindStateByEnv` 以 browser_id 为主键查找（frame_id 仅作兜底匹配）。
3. **渲染进程崩溃**：`OnRenderProcessTerminated` 不再回收通道（否则重载后无人读请求），只清空滞留的嵌套队列
   与 `execute_level`；通道随 `OnBeforeClose` 精确回收。
4. **渲染侧通道延迟到 `OnContextCreated` 建立**：`SyncChannel::Start(channel_key)` 可重建（换 key 时先 Stop 再重建）；
   未被使用的备用渲染进程不再创建无用通道。

**回归验证**：页面 5s 内 `readyState=complete`、`Extention` 为对象、全部同步调用结果正确；`jsapi_self_test` 仍 146/146。

### 14.5 多 web 页隔离与同步嵌套性能优化（v1.6）

**问题**：一个渲染进程可能承载多个浏览器（多窗口 / 多 web 页）。原实现每个渲染进程只持有一个
`SyncChannel`，后创建的页面会 `Start` 覆盖前一个页面的通道，导致多页同步调用互相串台。

**改造**：

1. **渲染进程按 browser_id 多通道**：`RendererCore` 改为 `map<browser_id, shared_ptr<SyncChannel>>`，
   每个浏览器独立通道、独立 watcher 线程、独立事件环形缓冲；`Binding` 持有所属 `channel`，
   `InvokeSync` 只用绑定自己的通道。同一渲染进程内的不同页面互不共享任何同步状态。
2. **Qt 宿主多页**：`--pages=N` 在一个窗口内用网格布局创建 N 个 `QtHostWidget`（各自独立 CefBrowser，
   实测各自独立渲染进程）；新增 `ResizeBrowserAt(index, rect)` / `GetBrowserAt(index)`，
   resize 时同步调整 CEF 子窗口并 `WasResized()`。
3. **同步嵌套示例**：`host` 节点新增 `syncEcho(text)` 与 `syncNest(depth, token)`，
   二者通过 `DispatchEventSync` 阻塞等待本页回调；页面上的 `sync-nest` 回调在内部再次调用 `syncNest`，
   形成 C++ → JS → C++ 的多层同步调用链。示例页新增「同步 RPC 嵌套调用」卡片（1/2/4 层、
   随机 20 次校验、耗时测试、自测）。

**验证结果（真实宿主 + CDP 模拟点击）**：

- 单页全按钮点击：全部动作执行成功；新增自测 `PASS 8 / FAIL 0`，随机嵌套 20 次全对；
  `syncNest(4,"T4") = d4>d3>d2>d1>leaf:T4`。
- 4 页 × 20s 满速随机调用（1~4 层嵌套、`mul`、`add` 混合）：15 191 次调用 `fail=0`，
  平均 0.31 ms、最大 16 ms；每页再各跑 500 次嵌套爆发，2 000 次全部正确。
- 3 页 × 10s：5 011 次调用 `fail=0`，平均 0.24 ms、最大 2.9 ms。
- 隔离断言：各页 token 互不串台（监听者返回值携带本页 tag），每页独立通道日志
  `sync channel ready, browser=1/2/3` 全部出现；`jsapi_self_test` 仍 146/146。

**性能优化（保持协议与语义不变）**：

1. 去掉每次 `Send` 前的 `ReplyReader::Reset()`：回包槽由 `seq` 精确匹配，超时残留的旧回包会被忽略，
   新回包直接覆盖，省掉一次命名互斥量往返。
2. 渲染侧等待由 `MsgWaitForMultipleObjects(..., wake mask = 0)` 改为 `WaitForMultipleObjects`：
   语义一致（都不派发窗口消息），少一次消息队列检查。

单页实测（3 轮中位数，单位 ms/次）：

| 场景 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| `host.mul`（纯同步） | 0.0320 | 0.0311 | -3% |
| `syncEcho`（1 层同步事件） | 0.0631 | 0.0553 | -12% |
| `syncNest(2)` | 0.1217 | 0.1107 | -9% |
| `syncNest(4)` | 0.2532 | 0.2144 | -15% |

每层嵌套成本约 0.055 ms，与单层往返基本一致，嵌套开销近似线性、无额外放大。

**测试注意**：多个 `jsapi_qt_host` 实例并发运行会共用 exe 同目录的 `cef_cache`，可能互相阻塞启动；
多实例验证必须串行执行。

### 14.6 可靠性与稳定性兜底（v1.7）

**目标**：插件函数耗时/异常、前端回调耗时/异常、页面崩溃、页面刷新等场景下，框架要么快速失败，要么自动恢复，不把故障放大成宿主崩溃或永久卡死。

1. **异常隔离**：`RpcHost::Process` 捕获插件函数体的 `std::exception` 与 `...`，分别转成
   `function 'x' threw: <what>` / `... threw: unknown exception`（getter/setter 同理），返回 `ok=false`
   而不是让异常穿透到会话线程导致进程终止。
2. **超时可配置**：`SyncChannel::Send(payload, seq, reply, error, timeout_ms)` 与
   `DispatchEventSync(..., timeout_ms)` 支持按调用指定超时（`<= 0` 用默认 10 s）。超时只放弃等待，
   不回滚已在执行的插件函数；迟到回包由 `seq` 校验丢弃（`ReplyReader::TryTake` 不匹配不消费），
   后续调用可立即恢复正常。
3. **崩溃隔离**：`OnRenderProcessTerminated` 保留通道（重载后仍由同一读取线程服务），但置
   `renderer_attached=false`：同步事件立刻以 `render process terminated` 失败、异步事件丢弃、
   嵌套/顶层队列清空、回包与事件环清空、监听器按浏览器清空。渲染侧 `seq` 改为时间戳播种，
   避免与上一进程的迟到回包撞号；`SyncChannel::Start` 在新进程接入时清掉残留回包与事件。
4. **导航/刷新一致性**：浏览器侧不再用「通道创建时缓存的 env」覆盖请求，改以渲染进程随请求上报的
   `(browser, frame)` 为准（仅 browser_id 以通道 key 校正）。新 document 建根对象（`describe(0)`）时，
   `JsRegistry::DiscardListeners(browser, frame)` 清掉同浏览器旧 frame 的监听器，避免事件命中
   已销毁的 `callback_id`（修复前表现为刷新后 `syncEcho` 报 `event callback not found`）。
5. **回归**：`jsapi_self_test` 187/187；真实 CEF 双文档导航回归 `PROBE-R2 PASS 16`；
   本地基线 `describe` 往返 ≈ 0.11 ms/次、JSON 编解码 ≈ 0.0008 ms/次。
   架构性约束（同页串行、超时不取消执行、跨页共享状态需加锁）记录在 `docs/接入指南.md` §7。
