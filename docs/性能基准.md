# JSAPI 跨进程 RPC 桥接性能报告

测量时间：2026-11-11
被测对象：本仓库（JSAPI RPC 桥接框架，渲染进程 V8 ↔ 浏览器进程插件）

---

## 1. 结论摘要

| 场景 | 中位耗时 | 说明 |
| --- | --- | --- |
| 同步空接口往返（JS 调用 → 回到 JS） | **30.3 µs** | 共享内存 + 命名事件 |
| 异步空接口往返（JS 调用 → Promise resolve） | **68.6 µs** | Chromium 进程消息（请求 + 回包） |
| 同步单程（估算） | **≈ 15 µs** | 往返的一半，上下行不可本地分离 |
| 异步单程（估算） | **≈ 34 µs** | 同上 |
| C++ 空函数体自身 | **0.29 ~ 0.37 µs** | 仅两次 `QueryPerformanceCounter` |
| C++ → JS 事件回调，空载单发 | **267 µs (p50) / 344 µs (均值) / 604 µs (p90)** | 跨线程投递 + 进程消息 |
| C++ → JS 事件回调，连续 300 条 | **1.57 ms (p50) / 2.76 ms (max)** | 含浏览器侧任务排队，吞吐 ≈ 11 万条/秒 |

要点：

- 同步 RPC 的纯桥接开销约 **30 µs**，其中 C++ 业务函数体几乎为 0，**耗时全部在桥接框架本身**（参数序列化、共享内存拷贝、事件唤醒、线程切换）。
- 异步 RPC 比同步慢 **2.3 倍（+38 µs）**，差距来自 Chromium 进程消息通道（`CefProcessMessage` + 渲染进程消息循环），而非插件执行。
- 反向通知（C++ → JS 事件）比同步往返高一个数量级（267 µs vs 30 µs）：它要经过 **插件执行线程（Worker 或 Qt GUI）→ CEF UI 线程 → 渲染进程主线程** 多次调度，且走的是异步 IPC，无法像同步 RPC 那样用共享内存直通。
- 事件批次吞吐能力充足（≈ 11 万条/秒），单条延迟主要被调度延迟而非数据量决定。

## 2. 测量口径

用户要求的是**纯桥接框架耗时**，因此：

- **不含节点 describe**：`Extention.demo.bench()` 在测试开始前取一次句柄，测量循环里只有方法调用。
- **空 C++ 接口**：`BenchNode::ping` / `pingAsync` 函数体只做两次 `QueryPerformanceCounter`，无业务逻辑、无字符串处理、无内存分配（非 trace 模式直接返回 `Int(1)`）。
- **空 JS 回调**：事件的 JS 监听器只做一次 `Map.set`，不做渲染、不打日志。
- 每个指标的 n、分位数、均值、标准差均记录在原始数据中。

## 4. 测量方法

### 4.1 为什么不能直接逐次计时

`performance.now()` 在渲染进程被 Chromium 量化为 **100 µs** 步长（实测样本值全部是 0 / 0.1 / 0.2 ms），而同步往返只有 30 µs 量级，逐次计时会退化为「0 或 100 µs」的二值噪声。

因此主指标采用**批量均值**：

- 同步：一轮连续调用 2000 次，用总耗时 / 次数得到单次均值，共 10 轮；
- 异步：一轮连续 `await` 500 次，共 10 轮。

这种方法牺牲了分布信息，但把时钟量化误差平摊到 2000 次上（≈ 0.05 µs），得到稳定的平均值。分布信息仍由逐次样本给出，仅作为上界参考。

### 4.2 跨进程时钟对齐与单程拆分

JS 与 C++ 位于不同进程，两个时钟（`performance.now()` 与 QPC）原点不同。

1. **对齐**：调用 `bench.clock()`（C++ 记录进入/返回两个 QPC 时刻），用 `(t0+t1)/2` 对 `(p0+p1)/2` 得到一次偏移估计；采样 200 次取均值。
2. **残差**：该偏移的残余系统偏差等于上下行不对称度的一半，**无法在本机内部消除**。
3. **拆分**：`ping(true)` 返回 `{t0, t1}`，
   - 去程 = `t0 − (p0 + offset)`
   - C++ 函数体 = `t1 − t0`
   - 回程 = 批量往返均值 − 去程 − C++ 函数体

由于 trace 变体要多构造并序列化一个对象，其往返（37.3 µs）略高于空接口（30.3 µs），拆分只在该变体内自洽，不能直接与空接口数值相加。

### 4.3 事件延迟测量

- **空载单发**：每次只 `emit(1)` 一条，等 JS 回调到达再发下一条，避免排队。延迟 = `(JS 回调时刻 + offset) − C++ 发布时刻`。
- **连续发布**：一次性 `emit(300)`，反映浏览器侧任务队列排队后的实际到达延迟与吞吐。

## 5. 同步 RPC 结果

| 指标 | 中位 | 3 轮实测（µs） |
| --- | --- | --- |
| 往返，批量均值（p50 of 10 轮） | **30.3 µs** | 29.6 / 30.3 / 31.9 |
| 往返，批量均值（3 轮中位数） | 31.9 µs | 45.5 / 31.5 / 31.9（首轮含一次 161 µs 抖动） |
| 往返，trace 变体 | 37.3 µs | 37.3 / 41.9 / 36.3 |
| 去程（JS 调用 → C++ 进入） | ≈ 4.6 µs | 4.6 / 14.2 / −9.5 |
| C++ 空函数体 | **0.29 µs** | 0.29 / 0.37 / 0.28 |
| 回程（C++ 返回 → JS 恢复） | ≈ 42 µs | 32.8 / 42.0 / 60.2 |
| 单次观测 p99（量化上界） | 0.2 ms | 0.2 / 0.4 / 0.2 |

说明：

- 去程/回程出现负值，直接暴露了对齐残差的量级（约 ±12 µs）；因此**单程只能按往返一半估计 ≈ 15 µs**，拆分数据仅用于判断「回程不比去程快」。
- 单次观测的 p99 = 0.2 ms 是量化上界：受 Chromium 定时器/调度抖动影响，偶发一次会被记为 100 µs 或 200 µs。
- 同步调用是**串行吞吐**模型：单线程约 **3.3 万次/秒**。

### 同步链路分解（30 µs 花在哪）

渲染进程 `InvokeSync` → 编码 JSON → 写共享内存 `request_map_` → `SetEvent` →
浏览器读取线程被唤醒 → `WaitForSingleObject(mutex)` → 读共享内存 → 解析 JSON → 投递会话线程 →
会话线程按线程亲和执行插件函数（Worker 直接执行；UI 亲和投递 **Qt GUI 线程**，`BlockingQueuedConnection`）→
写 `reply_map_` → `SetEvent` →
渲染进程 `WaitForSingleObject(event_, timeout)` 被唤醒 → 校验 `seq` → 解析回包 JSON → 转成 V8 值返回。

其中占主导的是**线程唤醒与跨线程投递**（两处事件等待 + 一次阻塞式跨线程投递），而不是数据拷贝或 JSON 解析——空接口的 payload 只有几十字节。

## 6. 异步 RPC 结果

| 指标 | 中位 | 3 轮实测（µs） |
| --- | --- | --- |
| 往返（JS 调用 → Promise resolve），批量均值 | **68.6 µs** | 68.8 / 66.4 / 68.6 |
| 往返，trace 变体 | 75.0 µs | 75.0 / 71.0 / 79.6 |
| 去程（估算） | ≈ 24.7 µs | 38.3 / 24.7 / 12.5 |
| C++ 空函数体 | 0.37 µs | 0.37 / 0.41 / 0.32 |
| 回程（估算） | ≈ 46.6 µs | 37.9 / 46.6 / 66.0 |
| 单次观测 p99（量化上界） | 0.3 ~ 1.2 ms | 0.3 / 1.2 / 0.5 |

### 与同步的差异来源

| 阶段 | 同步 | 异步 |
| --- | --- | --- |
| 请求通道 | 共享内存 + 命名事件 | `CefProcessMessage`（Chromium IPC，浏览器 UI 线程分发） |
| 渲染侧阻塞 | 是（`WaitForSingleObject`） | 否（立即返回 Promise，`pending_[seq]` 挂起） |
| 回包通道 | 共享内存 + 命名事件 | `CefProcessMessage` + 渲染进程消息循环 |
| 额外开销 | — | Promise 创建、`pending_` 插入/查找、V8 resolve 回调 |

**+38 µs 的差值基本等于「Chromium 进程消息往返」相对「共享内存往返」的差额**，插件执行时间（0.37 µs）可忽略。

注意：异步只是**渲染进程不阻塞**，浏览器侧仍是同步执行完再回包；若浏览器不回复，`pending_` 中的 Promise 不会超时，会永久挂起（异步通道当前无超时机制，渲染进程崩溃时随上下文释放）。

## 7. C++ → JS 事件回调结果

| 指标 | 中位 | 3 轮实测 |
| --- | --- | --- |
| 空载单发，p50 | **267 µs** | 267 / 278 / 225 |
| 空载单发，p90 | 604 µs | 604 / 667 / 508 |
| 空载单发，均值 | 344 µs | 344 / 366 / 268 |
| 空载单发，p99 | 1.16 ms | 1.16 / 1.19 / 0.72 |
| 连续 300 条，p50 | 1.57 ms | 1.67 / 1.57 / 1.54 |
| 连续 300 条，max | 2.76 ms | 2.76 / 3.04 / 2.33 |
| 连续 300 条总发布耗时（C++ 侧） | 0.4 ms | 0.4 / 0.5 / 0.4 |

解读：

- 单条事件延迟 **267 µs**，是同步往返的 **8.8 倍**。链路为：
  `BroadcastEvent`（插件执行线程）→ 写事件环形缓冲 → `CefPostTask` 投递到 **CEF UI 线程** → `SendProcessMessage(PID_RENDERER)` → 渲染进程主线程消息循环 → V8 回调。
  多次线程切换 + 一次异步 IPC，且中间没有可「直通」的共享内存同步等待。
- 连续发布 300 条时，事件在浏览器侧任务队列中排队，**全部送达耗时 2.76 ms**，对应吞吐 ≈ **11 万条/秒**；p50 1.57 ms 说明队列中位排队长度约 170 条。
- 事件延迟的分布比 RPC 更分散（p50 267 µs → p99 1.16 ms，4.3 倍），因为投递依赖 UI 线程调度，容易被同一线程上的其他任务推迟。

## 8. 与优化的关系

本报告的数据已经包含此前的两项优化：

1. **回包通道缓存**：`WriteSyncReply` 不再每次 `OpenFileMapping + MapViewOfFile + OpenEvent`（原每次 15~60 µs），改为按 map 名缓存句柄。若未优化，同步往返会落在 45~90 µs 区间。
2. **回包单次解析**：同步请求解析（`ProcessPayload`）复用已解析的 root，避免同一 payload 解析两次 JSON。

> 本报告数据采集于 2026-11-11。此后同步链路改为「读取线程 + 会话线程」读/执行分离，事件通道新增共享内存环形缓冲（`jsapi_evt_<key>`），主体耗时结构不变（仍是事件唤醒 + 跨线程调度）。每轮构建都可用下述自测基线做快速回归。

### 框架内部基线（`jsapi_self_test`）

不经过进程边界的核心层基线，用于防止回归（Release）：

| 指标 | 实测 | 阈值 |
| --- | --- | --- |
| 本地 `describe` RPC 往返（500 次均值） | ≈ **0.11 ms/次** | < 5 ms/次 |
| `JsValue` JSON 编码 + 解码（500 次均值） | ≈ **0.0008 ms/次** | < 1 ms/次 |

## 9. 测量局限

- **`performance.now()` 量化 100 µs**：所有「单次」分布只能作为上界，主指标依赖批量均值。
- **单程为估算**：跨进程时钟对齐含上下行不对称偏差（本机观测 ±12 µs），因此单程结论按「往返的一半」给出更稳妥。
- **空接口不代表业务开销**：真实接口会叠加参数序列化、业务逻辑和回包体积成本；本报告的数值是**桥接框架的下限**。
- **单机空闲环境**：未施加 CPU 争用、大 payload、多标签页并发；事件延迟对 UI 线程负载高度敏感，高负载下会显著上升。
- **首次调用含冷启动**：已做 30 次预热，但首轮的偶发 161 µs 抖动说明存在进程级调度尖峰，生产环境应关注 p99 而非均值。
